# CTD-AutoCompose

> ICH eCTD submission drafting service. Ingest CSRs, protocols, SAPs → auto-generate regulator-ready CTD sections with traced citations.

**Status:** prototype · backend API only · designed to plug into Biolevate's knowledge platform.

## What this does

Pharmaceutical sponsors spend 4–8 weeks compiling a Common Technical Document (CTD) for an NDA / MAA / J-NDA submission. The bottleneck isn't writing — it's *traceably* assembling content from dozens of source documents (CSRs, study protocols, statistical analysis plans, investigator brochures) into the rigid ICH eCTD format while maintaining citation integrity for regulator review.

This service automates the assembly step:

1. **Ingest** source documents (`POST /sources`)
2. **Extract** structured evidence (efficacy results, AE tables, study designs) per source
3. **Map** extracted evidence to the ICH eCTD module/section it belongs in
4. **Draft** each section with grounded LLM generation + inline citation markers
5. **Validate** the output against ICH eCTD format rules
6. **Export** the assembled submission (out of scope for this prototype)

Target outcome: 50% reduction in drafting time vs manual assembly. Every numeric or factual claim in the draft is traceable to a source paragraph chunk.

### Key design decisions

**Grounded generation, not free-form.** The drafter is constrained to evidence retrieved from indexed source docs (RAG pattern). The LLM is instructed to emit `[CITE:chunk-id]` markers inline; we parse those back into structured `Citation` objects. No claim survives without a source link.

**Citation graph as first-class artifact.** Citations are stored as edges (source paragraph → CTD section paragraph). At export, the graph becomes the eCTD hyperlink layer regulators expect for review.

**Async section drafting.** Each section drafts in parallel via `BackgroundTasks` with a concurrency semaphore. A full CTD (38 sections) runs in ~12 min vs 4–8 weeks manual. Production deployment would use Celery or arq for durable queues.

**Provider-agnostic LLM client.** `LLMClient` is an interface. Two implementations: `AnthropicClient` (Claude) and `MockClient` (deterministic fixtures). Customers with data-residency requirements can plug in on-prem providers without touching the drafter code.

**Mock LLM for local dev.** Set `LLM_PROVIDER=mock` in `.env` to run end-to-end without API keys. Drafter returns canned but realistic CTD content so the API surface is fully exercisable.

### What's stubbed for this prototype

- **Source extraction** (`extractor.py`): returns canned structured chunks per doc type. Production would use Biolevate's extraction pipeline (NLP + CV for tables/figures from PDF/DOCX).
- **Citation retrieval**: linear scan by doc_type. Production would use the published Biolevate graph-attention model + hybrid retrieval (BM25 + dense embeddings).
- **Storage**: in-memory `dict`. Production: Postgres + pgvector for embedding search.
- **Auth**: omitted. Production: OAuth2 via the customer's IdP (SSO).
- **Compliance rules**: 5 illustrative rules. Production: full ICH M4 + FDA/EMA/PMDA regional addenda.

## API

All endpoints under `/api/v1`. Full schema at `/docs` (auto-generated by FastAPI).

### Submissions
- `POST /submissions` — create new CTD submission
- `GET /submissions` — list submissions
- `GET /submissions/{id}` — get submission status + drafting progress
- `DELETE /submissions/{id}` — cancel & remove

### Sources
- `POST /submissions/{id}/sources` — ingest a source document
- `GET /submissions/{id}/sources` — list ingested sources

### Sections
- `GET /submissions/{id}/sections` — list all CTD sections + status
- `GET /submissions/{id}/sections/{section_id}` — get drafted section with citations
- `POST /submissions/{id}/sections/{section_id}/draft` — trigger draft (async)
- `POST /submissions/{id}/sections/{section_id}/regenerate` — regenerate with reviewer feedback
- `POST /submissions/{id}/draft-all` — draft every CTD section in parallel

### Compliance
- `GET /submissions/{id}/compliance` — validate against ICH eCTD rules

### Health
- `GET /health` — liveness
- `GET /health/ready` — readiness (LLM provider reachable, store connected)

## Example end-to-end

```bash
# 1. Create submission
curl -X POST http://localhost:8000/api/v1/submissions \
  -H "Content-Type: application/json" \
  -d '{
    "submission_id": "NDA-2026-08471",
    "compound": "BVL-2188",
    "indication": "Moderate-to-severe atopic dermatitis",
    "authority": "fda"
  }'
# → { "id": "<uuid>", ... }

# 2. Ingest a CSR
curl -X POST http://localhost:8000/api/v1/submissions/<uuid>/sources \
  -H "Content-Type: application/json" \
  -d '{
    "title": "CSR-2026-BVL-2188-P3",
    "doc_type": "csr",
    "content": "..."
  }'

# 3. Draft the Clinical Overview
curl -X POST http://localhost:8000/api/v1/submissions/<uuid>/sections/M2.5/draft \
  -H "Content-Type: application/json" \
  -d '{}'

# 4. Fetch the drafted section
curl http://localhost:8000/api/v1/submissions/<uuid>/sections/M2.5
# → { "id": "M2.5", "content": "BVL-2188 is a novel...", "citations": [...] }

# 5. Validate compliance
curl http://localhost:8000/api/v1/submissions/<uuid>/compliance
```

## Production considerations

| Concern         | Prototype       | Production                                              |
|-----------------|-----------------|---------------------------------------------------------|
| Storage         | in-memory dict  | Postgres + pgvector                                     |
| LLM calls       | single-shot     | Anthropic with prompt caching for ICH context (~70% savings) |
| Citations       | regex parse     | Structured tool-use output + GNN retrieval              |
| Background jobs | BackgroundTasks | Celery / arq with durable queue + retries               |
| Auth            | none            | OAuth2 + per-customer tenancy                           |
| Compliance      | 5 rules         | Full ICH eCTD v4.0 + regional addenda                   |
| Export          | none            | eCTD-compliant XML + leaf-PDFs (zipped)                 |
| Observability   | none            | OpenTelemetry traces, per-section token spend metrics   |
